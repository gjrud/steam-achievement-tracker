# Frontend

The frontend is a Svelte 5 single-page app in `frontend/`, built with Vite 8. It runs inside the Wails webview and communicates with the Go backend only through generated bindings and the `sync:changed` event. Backend contracts are described in [app-service.md](app-service.md) and [architecture.md](architecture.md).

## Directory map

```text
frontend/
  index.html                 mount point <div id="app">, loads src/main.js
  package.json               scripts, dependencies (@wailsio/runtime pinned to 3.1.0)
  vite.config.js             dev server, build, vitest config and test-only aliases
  jsconfig.json              editor settings only (checkJs and other compiler options); no typecheck script exists
  src/
    main.js                  imports style.css and app.css, mounts App.svelte
    App.svelte               root component: state, backend calls, routing between screens
    style.css                base element styles (html, body, form controls, selection)
    app.css                  application styles (~1570 lines); imported globally, not scoped
    vite-env.d.ts            Vite and Svelte type references
    lib/
      format.js  game.js  filter.js  tag.js  sync.js  disabled.js  update.js    pure helpers and the update store
      components/            13 Svelte components (see below)
    test/                    vitest setup, backend and runtime mocks, fixtures
  bindings/                  generated by `wails3 generate bindings` (git-ignored)
  dist/                      production build, embedded by main.go (git-ignored)
```

`App.svelte` is the only component that imports generated bindings:

```js
import {...} from '../bindings/github.com/gjrud/steam-achievement-tracker/app.js'
```

Child components receive data and callbacks through props. `@wailsio/runtime` is imported directly in `App.svelte` (`Events`), in `lib/update.js` (`Events`), and in `ApiKeyForm.svelte` and `UpdateBanner.svelte` (`Browser`).

## Screens and routing

`App.svelte` selects a screen from `state` (the most recent `GetAppState` result):

| Condition (first match wins) | Screen |
| --- | --- |
| `loading` | loading screen |
| `state.initError` | `SetupView mode="startup-error"` (shows the init error and the log file, or the app folder when no log file exists) |
| `!state.apiKeyPresent` | `SetupView mode="missing-key"` (key form, retry lookup; shows `apiKeyError` if set) |
| `!state.profileExists` | `SetupView mode="profile"` (SteamID input, Validate, Save and sync, Replace key) |
| otherwise | `DashboardShell` |

Overlays can appear above any screen: `ClearDataConfirmModal` (while `clearConfirmOpen`) and the game context menu (while `contextMenu` is set; rendered by `App.svelte` itself).

The update banner belongs to the dashboard only, and the Updates section belongs to Settings. Neither appears on the setup or startup-error screens. The update state is a separate store (see [Update banner and settings](#update-banner-and-settings)), not part of `state`.

## State model (App.svelte)

### State and the backend

- `state` holds the `GetAppState` result. Fields used: `apiKeyPresent`, `apiKeyError`, `profileExists`, `profile`, `dashboard`, `settings`, `syncInProgress`, `initError`, `logFile`, `dataDir`, `cacheDir`, `logDir`.
- `dashboard` holds `summary`, `suggestions`, `completed`, `warnings`, `disabled`, `latestSyncRun`.
- `$:` derives `dashboard`, `latestSyncRun`, `syncIsRunning`, `summary`, `completed`/`disabled` (sorted by title with `sortByTitle`; `suggestions` keeps the backend order), `warningGames` (`syncWarning` set), tag filter counts and visible chips, `filtered*` lists, `viewFiltered`, and `clearConfirmText` (the SteamID64, or the display name when there is no SteamID).

### Sync refresh (coalescing and events)

- `onMount` subscribes to `sync:changed` with `Events.On(syncChangedEvent, requestRefresh)` before the first read, so an event emitted during that read is not missed. The name is `syncChangedEvent = 'sync:changed'`, and the backend uses the same string (checked by a test).
- `requestRefresh` sets `refreshQueued` and calls `drainRefreshes`. A burst of events is coalesced into one read.
- `drainRefreshes` starts `refresh()` only when no read is in flight (`refreshing`), no action is in flight (`busyActions === 0`), and a read is queued.
- `refresh()` calls `GetAppState`. It discards a result if a newer request token exists (an action took over) and re-queues the read. A successful read clears a failed-read banner (`refreshError`).
- Failed reads: when `isSyncing(state)` is true, `scheduleRetry()` arms one `setTimeout` for `refreshRetryDelayMs = 2000`. The timer calls `requestRefresh`. Every call to `requestRefresh`, including each `sync:changed` event, cancels the pending timer and starts an immediate read (once no read or action is in flight). A successful read, or an action whose state is applied, also clears the timer. A failed action leaves it armed. A failed read while the last applied state shows no sync schedules nothing. Otherwise the retry continues until a read succeeds or an applied action replaces the state. The backend sync ending alone does not stop it, because `isSyncing` checks the last applied state. Unmount clears it.
- `isSyncing(s)` is true when `syncInProgress` is set or `latestSyncRun.status === 'running'`.

### Actions

Each backend action uses `beginAction()` / `endAction()`:

- `beginAction()` increments `busyActions`, clears `error` and `refreshError`, and takes a new `stateRequestToken`. Any in-flight read is dropped.
- `applyActionState(token, next)` stores the returned state only if the token is still current, and clears the retry timer.
- `endAction()` decrements `busyActions` and calls `drainRefreshes()`.

Actions: `retryKey` (`RetryAPIKey`), `validateProfile` (`ValidateProfile`, no begin/end: it only sets `validating` and `preview`), `saveProfile` (`SaveProfile`), `syncNow` (`SyncNow`), `saveLibrarySettings` (`SetLibrarySettings`), `confirmClearActiveUserData` (`ClearActiveUserData`), and `runGameAction` (`MarkGamePreviouslyCompleted`, `ToggleGameMissingAchievementsInDLC`, `DisableGame`, `EnableGame`).

`saveApiKey` is the exception: it calls `SaveAPIKey` without `beginAction`, so the form, not the app banner, shows failures. On success it clears `preview`, drops the error banner, and calls `requestRefresh`. It throws on failure so the form can display the error.

On a failed clear-data call the app re-reads state, because the backend may already have deleted the key before the failing step.

### Errors

- `error` is the single banner string shown in `DashboardShell` (`.error-banner`, `aria-live` polite) and in the setup screens.
- `refreshError` marks whether `error` came from a failed state read. Only such an error is cleared by a later successful read. An action error survives event-driven reads until the next action succeeds (test: `keeps an action error through event reads until a later action succeeds`).
- `formatMessage(err)` (in `format.js`) turns a rejection into text. A `RuntimeError` (Wails' kind for a bound method's returned error) and an `AppMessage` (thrown by the frontend with a sentence for the user, such as `A save is already in progress`) show their message. The backend guarantees that a `RuntimeError` from a bound method carries an app sentence: its errors go through `callBound` (see [app-service.md](app-service.md#error-boundary)), which also turns a Go panic into the generic sentence. Any other rejection, a missing one included, shows `genericMessage` (`Something went wrong. See the log file for details.`), so a JavaScript or argument error never shows its own text.

### Other interaction

- Global keydown (`handleGlobalKeydown`): Escape closes the context menu and the clear-data modal. In the list views (`suggestions`, `completed`, `warnings`, `disabled`), a printable key pressed outside a field or an interactive element focuses the view search box and appends the key.
- Context menu (`openGameMenu`): positioned at the pointer, then clamped to the viewport by `positionGameMenu` (12 px margin). The menu is `visibility: hidden` until positioned.
- Clear-data confirmation: `confirmClearActiveUserData` runs only when the typed text equals `clearConfirmText`. Switch values are passed as `ClearActiveUserData(deleteProfileData, deleteAPIKey)`.
- Tab change (`changeView`) resets the tag filter.

### Sync band wording

`syncBand` (`lib/sync.js`) builds the profile card's band from the latest run. The user guide describes these states in plain language; the table lists the strings produced by the code:

| Run state | Icon | Headline | Second line |
| --- | --- | --- | --- |
| `running`, total known | spin | `Syncing X / Y` | `detail` empty; time reads `Started <relative time>` |
| `running`, total not known yet | spin | `Sync running` | `detail` empty; time reads `Started <relative time>` |
| Run flag set, no run record yet | spin | `Sync starting` | `Starting sync…`, no time |
| No run stored | clock | `No sync yet` | `Press Sync now to fetch your library` |
| `success` | check | `All games synced` | `X / Y games`, omitted when the total is 0 |
| `partial` | warn | `Partial sync · N failed`, or `Partial sync` when N is 0 | `X / Y games synced` |
| `failed` | warn | `Sync failed · 1 error` or `Sync failed · N errors`, or `Sync failed` when N is 0 | `X / Y games synced` |
| `canceled` | stop | `Sync canceled` | `X / Y games synced` |
| Any other status | stop | The status text, or `Unknown` | `X / Y games synced` |

`countsOf` (`lib/sync.js`) returns an empty string whenever the run's total is 0. This applies to every finished state, not only `success`. The counts part of the second line is then omitted, and the band shows the headline and time only.

Time: a finished run is dated by `finishedAt` (or `startedAt` when that is missing); a running run by `startedAt`. An unparseable or missing time gives no time text. `formatRelativeTime` (`lib/format.js`) reads `just now` under a minute, `N min ago` under an hour, `1 hour ago` or `N hours ago` under a day, and `1 day ago` or `N days ago` under seven days. From seven days on it shows the absolute date and time from `formatDateTime`. `ProfileCard.svelte` also sets that absolute time as the hover title and re-evaluates the relative text every 30 s. Its live region changes only on a state transition, never with counts or time.

### Dashboard counters

`SummaryStats.svelte` displays three groups: **Library** (`All games`, `Purchased`), **Completed** (`Completed games`, `Completed sets`) and **Unlocked** (`Achievements`). The header stacks below 1180 px (`@media (max-width: 1180px)` in `app.css`).

### Svelte syntax

The components use legacy (non-runes) Svelte syntax: `export let` props, `$:` reactive statements, `on:` event directives, `<slot>` for item rendering, and `<script context="module">` for shared constants. Follow that style when adding or changing a component so the code stays consistent. `SummaryStats.svelte` is the only component that uses `{#snippet}` and `{@render}`. Do not copy that pattern into other components on its own; it would need a decision for the whole frontend.

## Incremental card grid

`IncrementalGrid.svelte` limits DOM size for large libraries. Constants are declared in a `<script context="module">` block so tests can import them. Only the Not completed and Completed tabs use it (`DashboardShell.svelte`); `SyncErrorsView` and `DisabledView` render every row.

| Constant | Value | Meaning |
| --- | --- | --- |
| `INITIAL` | 48 | Cards mounted on first render and after every reset. |
| `STEP` | 48 | Minimum cards added per growth step. |
| `SPACER_BIAS` | 0.99 | Scale on the estimated height of unmounted rows. Underestimating keeps scroll targets stable. |
| `ROOT_MARGIN_PX` (not exported) | 1500 | Observer margin: growth starts 1500 px before the sentinel reaches the viewport. |

Behavior:

- `limit` starts at `INITIAL`. `resetKey` (trimmed search text plus tag filter) resets it. Other refreshes keep the grown limit. Switching tabs remounts the grid, so it also starts at `INITIAL`.
- The `{#each}` renders `items.slice(0, limit)` and uses `entryKey` as the key.
- A "Show more (shown of total)" button and a spacer sit after the grid. The spacer's height reserves the space of unmounted rows so the document keeps its full height. It is computed from the average row pitch (row height plus row gap) and the column count from `getComputedStyle(...).gridTemplateColumns`.
- An `IntersectionObserver` watches the button box. On intersection, `grow(viewportBatch())` adds enough rows to clear the viewport plus the margin. If the box is already within that reach, the whole remainder loads. The observer is re-armed after each growth so growth continues while the box stays visible.
- A `ResizeObserver` re-measures on width changes.
- Without an `IntersectionObserver` (jsdom), only the button grows the list, by one `STEP`. Without a usable layout, observer hits and button clicks both add one `STEP`.
- Focus: when the button itself had focus and the list is complete, focus moves to the first newly revealed card with `preventScroll`, so the page does not jump.

## Styling

- `style.css`: base rules (html and body colors, font stack, `box-sizing`, form controls inherit font, selection color). It is the first import.
- `app.css`: all component classes (`game-card`, `profile-card`, `tab`, `banner`, `context-menu`, `confirm-modal`, etc.). The CSS is global, so class names must stay unique across components. `.sr-only` is defined here and used for screen-reader-only text.
- Tone classes (`tone-success`, `tone-warn`, and so on) come from `toneClass`.

## Error banners

Four kinds of messages can reach the user:

1. Startup error: `state.initError` on the startup-error screen.
2. Keyring error: `state.apiKeyError` on the missing-key screen.
3. Action or read error: `error` in `DashboardShell` (`.error-banner`). It is cleared by the next action and by a successful read when it came from a read.
4. Form errors: `ApiKeyForm` (`role="alert"`) and `SetupView` (`.error-text`).
5. Update errors: the update banner and the Settings section show the update sentence (see [Update banner and settings](#update-banner-and-settings)). They never use the sync `error` banner.

## Update banner and settings

The in-app updater (see [updater.md](updater.md)) has its own frontend state, separate from `GetAppState`. The backend behavior and phases are in the updater doc; this section describes what the frontend does with them.

### Store (`lib/update.js`)

- `createUpdateStore(api)` builds a Svelte store. `api` holds the bound calls (`getState`, `check`, `install(version)`, `cancel`, `restart`, `setChecksEnabled`), so the module imports no bindings. `App.svelte` passes `GetUpdateState`, `CheckForUpdates`, `InstallUpdate`, `CancelUpdate`, `RestartToUpdate` and `SetUpdateChecksEnabled`.
- `start()` subscribes to the Go event `update:changed` (`updateChangedEvent`, no payload) before its first read, then reads `GetUpdateState`. Every event triggers a read. Overlapping reads are allowed, and a read that finishes after a newer one was applied is dropped. A failed read keeps the last snapshot. `start()` returns the stop function, which `App.svelte` calls on unmount. The frontend never subscribes to the framework's `wails:updater:*` events. Until a read succeeds, `loaded` is false and no update UI shows.
- Every snapshot source (reads and the toggle's result) goes through one sequence guard, so an older result never overwrites a newer one.
- On a phase change the store clears `actionError` and `notice`. It sets `checkHeld` when a check starts over a visible `available` release or a displayed error; a check that starts from idle holds nothing. It clears `canceling` once the phase is no longer `downloading`, and it clears a "Later" dismissal when the snapshot's version differs.
- `acting` holds the bound call in flight: `check`, `install` or `restart`. A second check or install while one runs is ignored. `install` keeps `acting` for the whole download.
- `lastOp` records the last check or install the user started (`restart` does not change it). It is kept, not cleared, so the banner title does not flip while a retry runs.
- `check()` clears a "Later" dismissal when the check ends, so a found update shows again.
- `install(version)` passes the version the user saw. When the call ends with the snapshot `available` for a different version and no error, a notice asks the user to review that version and install again.
- `cancel()` sets `canceling` until the download ends. A rejected cancel clears it and shows the sentence.
- `restart()` is `RestartToUpdate`. A rejection shows its sentence and the staged update stays.
- `later()` hides the banner for the version on screen, in `available` only. It is in memory: a manual check that ends, a different version, or a relaunch brings the banner back. Nothing is persisted.
- `setChecksEnabled(enabled)` sets `savingChecks`, kept apart from `acting`, so a save and a check do not clear each other's marker. A second change while saving is ignored. A rejection shows its sentence in `settingsError` and keeps the stored value.
- Errors: a rejected call's text (`formatMessage`) goes to `actionError`; a rejection that is not a backend sentence shows the generic message. `updateError(view)` returns the snapshot's own `error` first, then `actionError`.
- Helpers:
  - `bannerVisible(view)`: false when not loaded or the updater is unavailable. `available` shows while its release is not dismissed. `checking` shows only when `checkHeld`. `downloading`, `verifying`, `installing`, `ready`, `restarting` and `error` always show. `idle` and `up-to-date` never show.
  - `checkLocked(phase)`: true in `checking`, `downloading`, `verifying`, `installing`, `ready` and `restarting`.
  - `retryKind(view)`: a failed check retries the check. A failed install retries the install of the version on screen, or a check when no release is known. With no operation started in this session (after a reload), a known release that is not notify-only means install, and anything else means check.
  - `readyLine(version)`: "Version X is ready. Restart to finish updating." (without a version: "Update ready. Restart to finish updating.").
  - `settingsStatus(view)`: the Settings status line.
  - `downloadFraction(progress)` (`null` when the total is unknown) and `formatBytes(n)`. `formatBytes` promotes to the next unit when rounding would read 1024, so 1048524 bytes reads "1.0 MB", not "1024 KB".

### Banner (`UpdateBanner.svelte`)

Rendered by `DashboardShell` above the tabs. It is the only place the dashboard shows update progress. It does not render on the setup or startup-error screens.

| Phase | Title | Detail | Buttons and link |
| --- | --- | --- | --- |
| `available` | Version X is available | "You have version Y.", plus "Download size Z." when the size is known | **Install** (not for notify-only), **Later**, and **Release notes** |
| `available`, notify-only | Version X is available | The notify reason | **Later** and **Release page** (no Install) |
| `checking` (only when `checkHeld`) | Checking for updates… | none | none |
| `downloading` | Downloading version X | "A of B (N%)" with a determinate meter; "A downloaded" when the total is unknown (indeterminate); "Preparing download…" before the first byte | **Cancel** (shows "Canceling…" until the download ends) |
| `verifying`, `installing` | Verifying download… / Installing update… | none (indeterminate meter) | none |
| `ready` | `readyLine` | Restarting closes the app and cancels a running sync. The update then applies. | **Restart now** |
| `restarting` | Restarting… | This can take up to 30 seconds. (indeterminate meter) | none |
| `error`, retry is install | Could not update to version X | The error sentence | **Try again** (install) and **Release page** |
| `error`, retry is check | Could not check for updates | The error sentence | **Try again** (check); **Release page** only when the build is notify-only |

- The release link needs a known release. It is shown in `available`, and in `error` when the retry is install or the build is notify-only. A failed check that found no release shows no link. Its label is "Release page" when the phase is `error` or the build is notify-only; otherwise "Release notes".
- The link keeps its real `href`. Clicks go to `Browser.OpenURL`, so the webview does not navigate. A failed open shows "Could not open the browser. Visit URL to read it." inline; the URL is never the last words of a sentence.
- `Install`, `Restart now` and `Try again` are disabled while `acting` is set. `Cancel` is disabled while `canceling` is set. `Later` is never disabled.
- The notice from `install()` shows as a plain line under the detail. A refusal from Go (busy, ready-first) shows its sentence in the banner and keeps the colour of an error. `ready` keeps the good-news colour.

Focus:

- A click on a button starts a change that removes or disables the button. The click marks the banner as pending focus; once the DOM has caught up, focus stays where it is if it is still on an enabled control in the banner. Otherwise it moves to the title (when the banner still shows) or to the host.
- The title has `tabindex="-1"` and is a focus target. The host `div` (`tabindex="-1"`) stays mounted while the banner is hidden. When the banner goes away with focus inside it, focus moves to the host before the DOM is removed, so focus never drops to the body.

Live region:

- The host is not a live region. One persistent visually hidden `<p role="status">` (`.sr-only`) stays mounted even while the banner is hidden. It announces the title, the notify reason (only for an `available` notify-only release), the error, the notice and the link error, joined, each ending with a full stop.
- Progress text (`aria-live="off"`) and the meter's value text are never in a live region. The title does not change during a download, so progress is not announced.

### Settings section (`UpdateSettings.svelte`)

Rendered by `SettingsView`, below the library sync section. It is hidden when the updater is unavailable in this build and before the first read succeeds.

- Current version (`unknown` when the snapshot has none).
- The switch **Check for updates on startup** (`role="switch"`). Its hint says the app contacts GitHub shortly after start and downloads nothing until Install. The box is `aria-busy` while saving. A click during a save is prevented, and after the call the box shows the stored value, so a rejected change snaps back.
- **Check now** uses `aria-disabled`, not `disabled`, so it keeps focus when clicked. It is disabled (`aria-disabled="true"`) while `checkLocked` or while `acting` is set. A click on a disabled button runs nothing. A save does not disable it.
- The status line shows `settingsStatus` as plain text, not a live region. A dismissed release reads "Press Check now to show it again."
- The live announcer is a persistent visually hidden `<p class="sr-only" role="status">` that repeats the status text only while the banner is hidden. While the banner shows, it is empty, so a phase is spoken once (by the banner), not twice. Its role is never toggled.
- Errors: a rejected toggle shows `settingsError` (`role="alert"`) always. The update error (`updateError`) shows as `role="alert"` only while the banner is hidden. While the banner shows the same error, Settings does not repeat it.

## Test setup (frontend/src/test)

| File | Purpose |

The test alias (`vite.config.js`, mode `test` only) maps `../bindings/.../app.js` to `wails-app-mock.js` and `@wailsio/runtime` to `wails-runtime-mock.js`. Test mode also sets the `browser` resolve condition, and jsdom is the environment.

Drift checks (`wails-bindings.test.js`):

- Every mock export exists in the generated bindings with the same argument count, and the mock uses no rest parameters.
- Every generated binding has a mock.
- Every name `App.svelte` imports exists in the generated bindings.
- `syncChangedEvent` in `app.go` equals the one in `App.svelte`.
- When `CI` is `1` or `true`, a missing `frontend/bindings` fails the suite. Locally, the generated-bindings tests are skipped.

When a backend binding changes: run `wails3 generate bindings`, then update `wails-app-mock.js` to match.
