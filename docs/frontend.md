# Frontend

The frontend is a Svelte 5 single-page app in `frontend/`, built with Vite 8. It runs inside the Wails webview and communicates with the Go backend only through generated bindings, the `sync:changed` and `update:changed` events, and `@wailsio/runtime` window and browser calls. Backend contracts are described in [app-service.md](app-service.md) and [architecture.md](architecture.md).

## Directory map

```text
frontend/
  index.html                 mount point <div id="app">, loads src/main.js
  package.json               scripts, dependencies (@wailsio/runtime pinned to 3.1.0)
  vite.config.js             dev server, build, vitest config and test-only aliases
  jsconfig.json              editor settings only (checkJs and other compiler options); no typecheck script exists
  src/
    main.js                  imports style.css and app.css, mounts App.svelte
    App.svelte               root component: state, backend calls, routing between screens, title bar and custom scrollbar
    style.css                base element styles (html, body, #app sizing, form controls, selection)
    app.css                  application styles; imported globally, not scoped
    vite-env.d.ts            Vite and Svelte type references
    lib/
      format.js  game.js  filter.js  tag.js  sync.js  disabled.js  update.js    pure helpers and the update store
      components/            15 Svelte components (see below)
    test/                    vitest setup, backend and runtime mocks, fixtures
  bindings/                  generated by `wails3 generate bindings` (git-ignored)
  dist/                      production build, embedded by main.go (git-ignored)
```

`App.svelte` is the only component that imports generated bindings:

```js
import {...} from '../bindings/github.com/gjrud/steam-achievement-tracker/app.js'
```

Child components receive data and callbacks through props. `@wailsio/runtime` is imported directly in `App.svelte` (`Events`), `lib/update.js` (`Events`), `lib/format.js` (`Call`), `TitleBar.svelte` (`Events`, `Window`), `ApiKeyForm.svelte` and `UpdateBanner.svelte` (`Browser`).

## Screens and routing

`App.svelte` selects a screen from `state` (the most recent `GetAppState` result):

| Condition (first match wins) | Screen |
| --- | --- |
| `loading` | loading screen |
| `state.initError` | `SetupView mode="startup-error"` (shows the init error and the log file, or the app folder when no log file exists) |
| `!state.apiKeyPresent` | `SetupView mode="missing-key"` (key form, retry lookup; shows `apiKeyError` if set) |
| `!state.profileExists` | `SetupView mode="profile"` (SteamID input, Validate, Save and sync, Replace key) |
| otherwise | `DashboardShell` |

The title bar ([Title bar and scroll layout](#title-bar-and-scroll-layout)) is rendered above every one of these screens, and the page content starts below it (the bar is `position: fixed`). The tabs and the Settings gear appear in the bar only on the dashboard.

Overlays can appear above any screen: `ClearDataConfirmModal` (while `clearConfirmOpen`) and the game context menu (while `contextMenu` is set; rendered by `App.svelte` itself).

The update banner belongs to the dashboard only, and the Updates section belongs to Settings. Neither appears on the setup or startup-error screens. The update state is a separate store (see [Update banner and settings](#update-banner-and-settings)), not part of `state`.

## State model (App.svelte)

### State and the backend

- `state` holds the `GetAppState` result. Fields used: `apiKeyPresent`, `apiKeyError`, `profileExists`, `profile`, `dashboard`, `settings`, `syncInProgress`, `initError`, `logFile`, `dataDir`, `cacheDir`, `logDir`.
- `dashboard` holds `summary`, `suggestions`, `completed`, `warnings`, `disabled`, `latestSyncRun`.
- `$:` derives `dashboard`, `latestSyncRun`, `syncIsRunning`, `summary`, `completed`/`disabled` (sorted by title with `sortByTitle`; `suggestions` keeps the backend order), `warningGames` (`syncWarning` set), tag filter counts and visible chips, `filtered*` lists, `viewFiltered`, and `clearConfirmText` (the SteamID64, or the display name when there is no SteamID). Tag chips exist only on Not completed and Completed; Sync errors and Disabled filter by search only, and the toolbar is hidden on Settings.

### Sync refresh (coalescing and events)

- `onMount` subscribes to `sync:changed` with `Events.On(syncChangedEvent, requestRefresh)` before the first read, so an event emitted during that read is not missed. The name is `syncChangedEvent = 'sync:changed'`, and the backend uses the same string (checked by a test).
- `requestRefresh` sets `refreshQueued` and calls `drainRefreshes`. A burst of events is coalesced into one read.
- `drainRefreshes` starts `refresh()` only when no read is in flight (`refreshing`), no action is in flight (`busyActions === 0`), and a read is queued.
- `refresh()` calls `GetAppState`. It discards a result if a newer request token exists (an action took over) and re-queues the read. A successful read clears a failed-read banner (`refreshError`).
- Failed reads: when `isSyncing(state)` is true, `scheduleRetry()` arms one `setTimeout` for `refreshRetryDelayMs = 2000`. The timer calls `requestRefresh`. Every call to `requestRefresh`, including each `sync:changed` event, cancels the pending timer and starts an immediate read (once no read or action is in flight). A successful read, or an action whose state is applied, also clears the timer. A failed action leaves it armed. A failed read while the last applied state shows no sync schedules nothing. Otherwise the retry continues until a read succeeds or an applied action replaces the state. The backend sync ending alone does not stop it, because `isSyncing` checks the last applied state. Unmount clears it.
- `isSyncing(s)` is true when `syncInProgress` is set or `latestSyncRun.status === 'running'`.

### Actions

Each backend action uses `beginAction()` / `endAction()`:

- `beginAction()` increments `busyActions`, clears `error` and `refreshError`, and takes a new `stateRequestToken`. Any in-flight read is dropped.
- `applyActionState(token, next)` stores the returned state only if the token is still current, and clears the retry timer.
- `endAction()` decrements `busyActions` and calls `drainRefreshes()`.

Actions: `retryKey` (`RetryAPIKey`), `validateProfile` (`ValidateProfile`, no begin/end: it only sets `validating` and `preview`), `saveProfile` (`SaveProfile`), `syncNow` (`SyncNow`), `saveLibrarySettings` (`SetLibrarySettings`), `confirmClearActiveUserData` (`ClearActiveUserData`), and `runGameAction` (`MarkGamePreviouslyCompleted`, `ToggleGameMissingAchievementsInDLC`, `DisableGame`, `EnableGame`).

`saveApiKey` is the exception: it calls `SaveAPIKey` without `beginAction`, so the form, not the app banner, shows failures. On success it clears `preview`, drops the error banner, and calls `requestRefresh`. It throws on failure so the form can display the error. While `savingKey` is set, `validateProfile` and `saveProfile` do nothing, the setup buttons are disabled, and a second `saveApiKey` throws `A save is already in progress`.

On a failed clear-data call the app re-reads state, because the backend may already have deleted the key before the failing step.

### Errors

- `error` is the single banner string shown in `DashboardShell` (`.error-banner`, `aria-live` polite) and in the setup screens.
- `refreshError` marks whether `error` came from a failed state read. Only such an error is cleared by a later successful read. An action error survives event-driven reads until the next action succeeds (test: `keeps an action error through event reads until a later action succeeds`).
- `formatMessage(err)` (in `format.js`) turns a rejection into text. A `RuntimeError` (Wails' kind for a bound method's returned error) and an `AppMessage` (thrown by the frontend with a sentence for the user, such as `A save is already in progress`) show their message. The backend guarantees that a `RuntimeError` from a bound method carries an app sentence: its errors go through `callBound` (see [app-service.md](app-service.md#error-boundary)), which also turns a Go panic into the generic sentence. Any other rejection, a missing one included, shows `genericMessage` (`Something went wrong. See the log file for details.`), so a JavaScript or argument error never shows its own text.

### Other interaction

- Global keydown (`handleGlobalKeydown`): Escape closes the context menu and the clear-data modal. In the list views (`suggestions`, `completed`, `warnings`, `disabled`), a printable key pressed outside a field or an interactive element focuses the view search box and appends the key.
- Context menu (`openGameMenu`): opened by right-click on a card or sync-error row (not on disabled rows, which have a Re-enable button). Positioned at the pointer, then clamped to the viewport by `positionGameMenu` (12 px margin). The menu is `visibility: hidden` until positioned. The top clamp starts below the title bar, and the bottom clamp uses `window.innerHeight`. A mousedown on the title bar closes it (see [Title bar and scroll layout](#title-bar-and-scroll-layout)). Items: in Not completed only, Mark as previously completed (or Clear previously completed flag) and Flag missing achievements in DLC (or Clear DLC-missing flag); in every view with a menu, Disable game or Disable set, or Re-enable game or Re-enable set on a disabled game.
- Clear-data confirmation: `confirmClearActiveUserData` runs only when the typed text equals `clearConfirmText`. Switch values are passed as `ClearActiveUserData(deleteProfileData, deleteAPIKey)`. On success the view returns to Not completed, and the tag filter, profile input and preview are cleared. On failure the dialog closes so the error banner shows, and the state is re-read.
- Tab change (`changeView`, from a tab or the gear) does nothing when the view is already active. Otherwise it scrolls to the top and clears the tag filter. Focus behaviour is in [Title bar and scroll layout](#title-bar-and-scroll-layout).

### Sync band wording

`syncBand` (`lib/sync.js`) builds the profile card's band from the latest run. The table lists the strings produced by the code. In every finished state the counts are omitted when the run's total is 0 (`countsOf`), leaving the headline and time:

| Run state | Icon | Headline | Second line |
| --- | --- | --- | --- |
| `running`, total known | spin | `Syncing X / Y` | `detail` empty; time reads `Started <relative time>` |
| `running`, total not known yet | spin | `Sync running` | `detail` empty; time reads `Started <relative time>` |
| Run flag set, no run record yet | spin | `Sync starting` | `Starting sync…`, no time |
| No run stored | clock | `No sync yet` | `Press Sync now to fetch your library` |
| `success` | check | `All games synced` | `X / Y games`, omitted when the total is 0 |
| `partial` | warn | `Partial sync · N failed`, or `Partial sync` when N is 0 | `X / Y games synced` |
| `failed` | warn | `Sync failed · 1 error` or `Sync failed · N errors`, or `Sync failed` when N is 0 | `X / Y games synced` |
| `canceled` | stop | `Sync canceled` | `X / Y games synced` |
| Any other status | stop | The status text, or `Unknown` | `X / Y games synced` |

Time: a finished run is dated by `finishedAt` (or `startedAt` when that is missing); a running run by `startedAt`. An unparseable or missing time gives no time text. `formatRelativeTime` (`lib/format.js`) reads `just now` under a minute, `N min ago` under an hour, `1 hour ago` or `N hours ago` under a day, and `1 day ago` or `N days ago` under seven days. From seven days on it shows the absolute date and time from `formatDateTime`. `ProfileCard.svelte` also sets that absolute time as the hover title and re-evaluates the relative text every 30 s. Its live region changes only on a state transition, never with counts or time.

### Dashboard counters

`SummaryStats.svelte` displays three groups: **Library** (`All games`, `Purchased`), **Completed** (`Completed games`, `Completed sets`) and **Unlocked** (`Achievements`). A completed counter shows `vetted (total)` only when some counted entries are unvetted. Its hover title and screen-reader text say `N vetted of M total`. The header stacks below 1180 px (`@media (max-width: 1180px)` in `app.css`).

| `untouched` | Untouched |
| `unvetted` | Unvetted |
| `no_achievements` | No achievements |
| `set` | Set |

### Svelte syntax

The components use legacy (non-runes) Svelte syntax: `export let` props, `$:` reactive statements, `on:` event directives, `<slot>` for item rendering, and `<script context="module">` for shared constants. Follow that style when changing a legacy component so the code stays consistent. `SummaryStats.svelte` is the only component that uses `{#snippet}` and `{@render}`. Do not copy that pattern into other components on its own; it would need a decision for the whole frontend.

`TitleBar.svelte` and `ScrollBar.svelte` are written with runes (`$props`, `$state`, `onclick`/`onmousedown` attributes). New components use runes; a legacy component that is touched stays legacy until a separate runes migration.

## Incremental card grid

`IncrementalGrid.svelte` limits DOM size for large libraries. Constants are declared in a `<script context="module">` block so tests can import them. Only the Not completed and Completed tabs use it (`DashboardShell.svelte`); `SyncErrorsView` and `DisabledView` render every row.

| Constant | Value | Meaning |
| --- | --- | --- |
| `INITIAL` | 48 | Cards mounted on first render and after every reset. |
| `STEP` | 48 | Minimum cards added per growth step. |
| `SPACER_BIAS` | 0.99 | Scale on the estimated height of unmounted rows. Underestimating keeps scroll targets stable. |
| `ROOT_MARGIN_PX` (not exported) | 1500 | Observer margin: growth starts 1500 px before the sentinel reaches the viewport. |

Behavior:

- `limit` starts at `INITIAL`. `resetKey` (trimmed search text plus tag filter) resets it. Other refreshes keep the grown limit. Switching tabs remounts the grid, so it also starts at `INITIAL`.
- The `{#each}` renders `items.slice(0, limit)` and uses `entryKey` as the key.
- A "Show more (shown of total)" button and a spacer sit after the grid. The spacer's height reserves the space of unmounted rows so the list keeps its full height. It is computed from the average row pitch (row height plus row gap) and the column count from `getComputedStyle(...).gridTemplateColumns`.
- Scroll root: the document. The `IntersectionObserver` has no `root` (the viewport) and uses `rootMargin` `ROOT_MARGIN_PX`. It is created at component init (none in jsdom).
- An `IntersectionObserver` watches the button box. On intersection, `grow(viewportBatch())` adds enough rows to clear the viewport plus the margin. If the box is already within that reach, the whole remainder loads. The observer is re-armed after each growth so growth continues while the box stays visible.
- `viewportBatch` reads `window.innerHeight` as the bottom of the visible area. The document scrolls, so that is the real bottom of the viewport. The fixed title bar covers the top 42 px, which only makes the batch marginally larger than needed.
- A `ResizeObserver` re-measures on width changes.
- Without an `IntersectionObserver` (jsdom), only the button grows the list, by one `STEP`. Without a usable layout, observer hits and button clicks both add one `STEP`.
- Focus: when the button itself had focus and the list is complete, focus moves to the first newly revealed card with `preventScroll`, so the page does not jump.

## Title bar and scroll layout

The window's top edge is an app-drawn bar (`TitleBar.svelte`, height `--title-bar-height` = 42 px, defined in `style.css`). The same bar shows on every screen. The window is frameless (see [app-service.md](app-service.md)), so this bar replaces the native title bar.

**Structure.** The document scrolls (`html` is the scroller). An inner scroll container is not used: dragging an inner `overflow: auto` box's thumb is choppy in WebKitGTK. The bar is `position: fixed` (top, left and right 0, `z-index` 1100), so scrolling never moves it, and `#app` has `padding-top: var(--title-bar-height)` so the content starts below it. `html` has `scroll-padding-top: calc(var(--title-bar-height) + var(--title-fade-height))`, so keyboard focus, find-in-page and `scrollIntoView` stop short of the bar and the fade under it. The loading, setup and startup-error screens use `min-height: calc(100vh - var(--title-bar-height))`, so together with the padding they fill exactly one window. The native document scrollbar is hidden (`html::-webkit-scrollbar { width: 0; height: 0 }` in `style.css`), so the content keeps the full window width, and `ScrollBar.svelte` draws the bar instead, starting at the top of the content (`--content-top-gap` below the bar).

**Content.**

- Icon: the title bar icon, `frontend/src/assets/appicon.svg`, imported by `TitleBar.svelte` and drawn as tall as the bar (`--title-bar-height`, 42 px). It is the title bar's own artwork (no background tile), not a copy of `build/appicon.svg`. The ring and trophy fill about 69% of the viewBox, so the ring is about 29 px across its outer edge, centred on the bar's middle line. It is not made taller than the bar: the span's auto grid row would grow to the image and be aligned to the top of the span, so it would sit off the centre line. Its top-left arc reaches about 3.6 px into Wails' 15x15 top-left resize corner zone, so a press there starts a resize, not a drag. It is decorative (`alt=""`, `aria-hidden`, `draggable="false"`) and has `pointer-events: none`, so a press on it targets the icon span, which is the drag handle. Do not overwrite it when the app icon changes.
- Tabs (dashboard only): `<nav aria-label="Dashboard views">` with four buttons: Not completed, Completed, Sync errors, Disabled. The active one has `aria-current="page"`. The nav is not an ARIA tablist. The view ids are the ones the code already used (`suggestions`, `completed`, `warnings`, `disabled`).
- Settings gear (dashboard only): `aria-label="Settings"`, with `aria-current="page"` while Settings is open. Settings is reached only through the gear; there is no Settings tab.
- Window controls, on every screen: Minimize (`aria-label="Minimize"`), Maximize or Restore (`aria-label` follows the state), Close (`aria-label="Close"`). They are real `<button type="button">` elements with `tabindex="-1"`: keyboard users use the OS window shortcuts, but the names are still exposed. Each has a `title` tooltip with the same text as its label (the Maximize or Restore tooltip follows the state), like the gear's.
- Non-dashboard screens (loading, startup error, missing key, profile setup) show the icon and the controls only.

**Window calls and maximise state.** The controls call `Window.Minimise()`, `Window.ToggleMaximise()` and `Window.Close()` from `@wailsio/runtime`. Maximise state comes from `Window.IsMaximised()`, read once at mount. It is read again, 120 ms after the last event, on each of `common:WindowMaximise`, `common:WindowUnMaximise` and `common:WindowRestore` (`Events.Types.Common`). Windows sends `WindowRestore` during a live resize and on keyboard snap, so all three are needed. The listeners are removed on unmount. The state only drives the label and the glyph.

**Drag.** The bar has `--wails-draggable: drag`. Every bar button has `--wails-draggable: no-drag`. The value is a custom property, so it is inherited: the icon span, the gaps between tabs and the empty fill drag, and the buttons do not. `user-select: none` is set on the bar. The runtime reads the computed value (`node_modules/@wailsio/runtime/dist/drag.js`). jsdom does not load CSS, so drag is a manual check ([testing.md](testing.md#title-bar-manual-checks)). Double-click on the empty bar does nothing: Wails' double-click handler is macOS-only.

**Scroll fade.** `.title-bar::before` is a strip `--title-fade-height` (20 px, in `style.css`) tall, just under the bar (`top: 100%`): the page colour fading to clear, so cards scrolling up under the bar fade out instead of stopping at a hard edge. It is almost clear by 14 px (about 10 % opacity), the gap under the bar at the top of the dashboard, so the heading at rest is barely dimmed. It has `pointer-events: none` and lies outside the bar's box, so drag and clicks underneath are unaffected. It stops 20 px short of the right edge (`--resize-inset-right` plus the scrollbar's 14 px width), so the custom scrollbar's thumb is not faded; no content sits in that strip at the supported widths (the dashboard has a 28 px right margin above 720 px, and the window's minimum width is 900 px). It is part of the bar, so it draws above the context menu (z-index 1100 against 1000) and fades the top of a menu that sits within 20 px of the bar; the menu clamps at the bar height plus a 12 px margin, so a menu whose top is within 8 px of the clamp has its top edge faintly dimmed (at most about 25 %).

**Bottom fade.** `body::before` (`style.css`) mirrors the scroll fade at the bottom edge of the window: a `position: fixed` strip `--title-fade-height` (20 px) tall, with the same gradient stops flipped (`to top`), so it is clear at its top and the page colour at the window's bottom edge, and content scrolling down fades out instead of stopping at a hard edge. It is nearly clear by 14 px from the edge, and `.app-shell` has 28 px of bottom padding (the setup and loading screens 32 px), so the last row at the end of the page is not dimmed. Like the top fade it has `pointer-events: none` and stops 20 px short of the right edge (`--resize-inset-right` plus the scrollbar's 14 px width), so the custom scrollbar's thumb is not faded. `z-index` is 800: over the page, under the scrollbar (900), the context menu (1000), the title bar (1100) and the modal backdrop (1200). Unlike the top fade it is not part of the bar, so it never fades a context menu.

**Window outline.** `body::after` (`style.css`) draws a 1 px border around the whole window (`position: fixed; inset: 0`, `pointer-events: none`, the highest `z-index`), so the frameless window has a visible edge on a dark desktop. Its colour is `--window-line-color` (`#2d4560`, in `:root`), the same variable as the title bar's bottom line (`.title-bar::after`), the border of the active tab and gear, and the divider between the bar's controls, so these always match. It is drawn above everything, including the modal backdrop and the window's close button, and it is not hidden when the window is maximized. It does not intercept presses, so Wails' edge resize zones and drag are unaffected.

**Press and focus.**

- A mousedown on the bar calls `preventDefault`, so focus stays in a search box or modal input. The Wails drag handler listens in the capture phase, so it still starts the drag. Clicks on buttons still fire.
- The same mousedown closes the game context menu (`closeGameMenu`), because a bar drag fires no `click` for the window-level handler to see.
- A tab or gear click does not move focus onto the button (the bar cancels the mousedown focus change, above), so focus stays on the body or wherever it was. PgUp, PgDn, Home, End, Space and the arrow keys scroll the document natively from there, and a printable key starts the search as it does from the body. A tab reached by keyboard keeps its focus after Enter.

**Modal.** While `ClearDataConfirmModal` is open, the tabs and the gear are `disabled` (`disabled` is used, not `inert`, because jsdom does not apply `inert`). The window controls stay live, so the window can still be moved, minimised or closed. The modal backdrop is `inset: var(--title-bar-height) 0 0 0`, so it starts below the bar. The backdrop's one grid row is `minmax(0, 1fr)`, so the grid area has a definite height (the backdrop's content box: the window height less the bar and 40 px of padding). The dialog's `max-height: 100%` caps it at that height, which replaces `calc(100vh - 40px)`. The dialog scrolls inside itself when it is taller.

**Resize zones.** Wails' resize zones are 5 px along each edge and 15 px at each corner (5 px plus `cornerExtra` 10 px), measured from the window edge (`node_modules/@wailsio/runtime/dist/drag.js`). Tuning is left at the Wails defaults; no `Options.Flags` changes. Part of the close button lies in the right resize zone; a plain click still fires.

**Custom scrollbar (`ScrollBar.svelte`).** The native scrollbar is hidden, so Wails' document-scrollbar mitigation (`node_modules/@wailsio/runtime/dist/drag.js` measures `innerWidth - clientWidth`) sees 0 and does nothing; the custom bar has to stay out of the zones itself. It is `position: fixed` with `top: calc(var(--title-bar-height) + var(--content-top-gap))`, `right: var(--resize-inset-right)` (6 px) and `bottom: var(--resize-inset-bottom)` (15 px), both variables in `style.css`. A corner zone is a 15x15 px square that needs both: within 15 px of the right edge and within 15 px of the top or bottom edge. The 6 px right inset clears the 5 px right strip, but the bar is inside the 15 px right column, so the track must stay out of the corner squares: the 15 px bottom inset puts its end exactly above the bottom-right square. At the top the bar starts at y = 56 (the title bar's 42 px plus `--content-top-gap`, 14 px, so it lines up with the top of the dashboard content), so the window's 5 px top strip does not reach it, and the top-right square lies under the title bar's close button. `--wails-draggable: no-drag` is set on it, and a press on it calls `preventDefault` on `pointerdown` (which also cancels the compatibility `mousedown`). The geometry, not that, is what keeps it out of the zones. If Wails' zone sizes change, update the two variables (see [upgrading Wails](build-and-release.md#upgrading-wails)).

It mirrors the page and does not replace native scrolling: wheel, keys, touch and find-in-page scroll the document, and a wheel over the bar reaches the document too (it is a fixed element). It is therefore `aria-hidden="true"` and not focusable.

- Geometry and look: a 14 px hit area in every state (hover and drag only change colour, so nothing shifts), a faint 8 px rounded groove (`::before`, `rgba(159, 183, 204, 0.06)`), and an 8 px rounded thumb (a 14 px box with 3 px transparent borders and `background-clip: padding-box`). The thumb is steel blue (`#3a566f`) at rest, lighter (`#5b7f9d`) on hover and the accent blue (`#66c0f4`) while dragged. The bar occupies x from W-20 to W-6, y from 56 to H-15. `z-index` is 900: over the page, under the context menu (1000), the title bar (1100) and the modal backdrop (1200).
- Size and position: thumb height is `max(48 px, track * viewport / page)`, so it stays grabbable on a list of thousands of games. Its offset is `scrollY / (page - viewport)` of the thumb travel (`track - thumb`).
- Updates: a passive `scroll` listener and a `resize` listener, plus a `ResizeObserver` on `documentElement` and `body` (the incremental grid grows the page; no observer exists in jsdom, and the component works without one). All of them go through one `requestAnimationFrame`, so there is one update per frame.
- Hidden (`visibility: hidden`, so it keeps a measurable height) when the page does not overflow, for example on Settings.
- Drag: `pointerdown` on the thumb (primary button) captures the pointer and records the pointer's y and the thumb offset. Each `pointermove` re-reads the metrics (the page can grow mid-drag) and calls `window.scrollTo({top, behavior: 'instant'})` with `top = (thumbOffset + pointerDelta) / travel * (page - viewport)`, clamped to the page. `pointerup`, `pointercancel` and lost capture end the drag, and so does a `pointermove` with no button held (a missed release, when capture failed).
- Track click: a press on the track outside the thumb pages by one track height toward the press (`scrollTo`, clamped). The track runs from the top of the content (title bar plus `--content-top-gap`) to the bottom inset, so no content is skipped under the bar. There is no hold-to-repeat.
- `scrollbar-width` and `scrollbar-color` are deliberately not set: Chromium 121+ ignores `::-webkit-scrollbar` once either is set.

Visual and drag checks on WebView2 and WebKitGTK are manual ([testing.md](testing.md#title-bar-manual-checks)); jsdom does not draw scrollbars.

**Margins.** With the native bar hidden the content has the whole window width. `.app-shell` has `padding: var(--content-top-gap) 28px 28px` (`--content-top-gap` is 14 px, and 9 px under 720 px, where the side and bottom padding is 18 px), so the dashboard is 28 px from the left, right and bottom window edges and 14 px below the title bar (the sides set the card width; the top is only the gap under the bar). At a 1210 px window the content is 1154 px wide (1210 less 2 × 28). `.game-grid` (`app.css`) fits five columns there (minimum card 210 px, gap 16 px), so each card is (1154 − 4 × 16) / 5 = 218 px. A tag such as "New achievements added" stays on one line if the card is about 217.5 px or wider; the five cards plus gaps then need about 1151.5 px of content, so there is 2.5 px of slack: each side margin can grow by about 1.25 px (or one side by 2.5 px) before the tag wraps. The custom scrollbar is fixed and takes no layout space, so it never narrows the cards (it can overlap the 28 px right margin, which is empty).

**Narrow width.** At 1040 px and below, tab padding and tracking shrink. A label that still does not fit is cut with an ellipsis. Icon, tabs, gear and controls never wrap (`.title-bar` is one non-wrapping flex row), and the controls keep their width.

**Sizes and look.** Every item sits on one centre line, y = 21 px: the icon, the tab labels, the gear glyph and the three control glyphs. The bar has no CSS border. Its bottom line is a 1 px `::after` inside the 42 px, so the centre is a whole pixel and 1 px strokes stay sharp. The icon span and the three window controls run the full 42 px height (centred by the grid). Tabs and the gear are folder tabs from 6 px (below Wails' 5 px top resize strip) to the bar's bottom edge, 36 px tall: a 1 px top border plus 7 px bottom padding put their content box on 7 to 35, whose middle is 21. The active tab (and the active gear) is page-coloured with an accent cap, and covers the bar's bottom line so it opens into the page; the bar's buttons are `position: relative; z-index: 1` over that line. Tabs and gear share hover and active rules. Widths: the gear and the controls are all 46 px; the divider is 1 px by 20 px with 4 px each side; tabs are 2 px apart. Glyphs: the controls are 12 px with a 1.2 px stroke; the gear is drawn at 14 px with stroke-width 1.37 (1.2 px on screen), so its ink is about 12 px against the controls' 10 px squares. Type: the bar is 13 px, tabs inherit it (700 weight, 0.08em tracking, uppercase); at 1040 px and below they drop to 12 px. Tab labels stay uppercase: they fit at 900 px with the shrink rule above. The bar's z-index (1100) keeps it above the context menu (1000).

**Design decisions.**

- The bar has no window-blurred style.
- Viewport height: `window.innerHeight` stays for `viewportBatch` and `positionGameMenu` (the document scrolls, so it is the viewport height).
- Scroll position across views: reset to the top when the view changes (`changeView` in `App.svelte`, a tab or the gear), so a new view never opens already scrolled. The scroll position within a view is not remembered when you come back to it.
- Background colours: the page keeps `#0b141f` (`style.css`), and the window keeps `RGB(27, 38, 54)` (`window.go`). The bar uses the page colour so the active tab reads as part of the page.
- No native (GTK or compositor) border is added; the only edge is the app-drawn 1 px outline (`body::after`).

**Window creation.** The window is frameless, so this bar is the only title bar and its controls are the window's only on-screen controls. Creation is in `window.go` and is described in [app-service.md](app-service.md). If the frontend fails to load, the window has no controls; only window-manager shortcuts remain (no native fallback). On Linux the window is still shown in that case, because it is shown on `WindowLoadFinished`.

## Styling

Its `:root` variables are `--title-bar-height` (42 px), `--title-fade-height` (20 px, the fade under the bar), `--content-top-gap` (14 px, 9 px under 720 px: the space under the bar above the content, also where the custom scrollbar starts), the custom scrollbar's resize insets `--resize-inset-right` (6 px) and `--resize-inset-bottom` (15 px), and `--window-line-color` (`#2d4560`, the window outline and the title bar's lines). It also hides the native document scrollbar, pads `#app` below the fixed bar, and draws the bottom fade (`body::before`) and the window outline (`body::after`, see [Title bar and scroll layout](#title-bar-and-scroll-layout)).

## Error banners

Five kinds of messages can reach the user:

1. Startup error: `state.initError` on the startup-error screen.
2. Keyring error: `state.apiKeyError` on the missing-key screen.
3. Action or read error: `error` in `DashboardShell` (`.error-banner`). It is cleared by the next action and by a successful read when it came from a read.
4. Form errors: `ApiKeyForm` (`role="alert"`) and `SetupView` (`.error-text`).
5. Update errors: the update banner and the Settings section show the update sentence (see [Update banner and settings](#update-banner-and-settings)). They never use the sync `error` banner.

## Update banner and settings

The in-app updater (see [updater.md](updater.md)) has its own frontend state, separate from `GetAppState`. The backend behavior and phases are in the updater doc; this section describes what the frontend does with them.

### Store (`lib/update.js`)

- `createUpdateStore(api)` builds a Svelte store. `api` holds the bound calls (`getState`, `check`, `install(version)`, `cancel`, `restart`, `setChecksEnabled`), so the module imports no bindings. `App.svelte` passes `GetUpdateState`, `CheckForUpdates`, `InstallUpdate`, `CancelUpdate`, `RestartToUpdate` and `SetUpdateChecksEnabled`.
- `start()` subscribes to the Go event `update:changed` (`updateChangedEvent`, no payload) before its first read, then reads `GetUpdateState`. Every event triggers a read. Overlapping reads are allowed, and a read that finishes after a newer one was applied is dropped. A failed read keeps the last snapshot. `start()` returns the stop function, which `App.svelte` calls on unmount. The frontend never subscribes to the framework's `wails:updater:*` events. Until a read succeeds, `loaded` is false and no update UI shows.
- Every snapshot source (reads and the toggle's result) goes through one sequence guard, so an older result never overwrites a newer one.
- On a phase change the store clears `actionError` and `notice`. It sets `checkHeld` when a check starts over a visible `available` release or a displayed error; a check that starts from idle holds nothing. It clears `canceling` once the phase is no longer `downloading`, and it clears a "Later" dismissal when the snapshot's version differs.
- `acting` holds the bound call in flight: `check`, `install` or `restart`. A second check or install while one runs is ignored. `install` keeps `acting` for the whole download.
- `lastOp` records the last check or install the user started (`restart` does not change it). It is kept, not cleared, so the banner title does not flip while a retry runs.
- `check()` clears a "Later" dismissal when the check ends, so a found update shows again.
- `install(version)` passes the version the user saw. When the call ends with the snapshot `available` for a different version and no error, a notice asks the user to review that version and install again.
- `cancel()` sets `canceling` until the download ends. A rejected cancel clears it and shows the sentence.
- `restart()` is `RestartToUpdate`. A rejection shows its sentence and the staged update stays.
- `later()` hides the banner for the version on screen, in `available` only. It is in memory: a manual check that ends, a different version, or a relaunch brings the banner back. Nothing is persisted.
- `setChecksEnabled(enabled)` sets `savingChecks`, kept apart from `acting`, so a save and a check do not clear each other's marker. A second change while saving is ignored. A rejection shows its sentence in `settingsError` and keeps the stored value.
- Errors: a rejected call's text (`formatMessage`) goes to `actionError`; a rejection that is not a backend sentence shows the generic message. `updateError(view)` returns the snapshot's own `error` first, then `actionError`.
- Helpers:
  - `bannerVisible(view)`: false when not loaded or the updater is unavailable. `available` shows while its release is not dismissed. `checking` shows only when `checkHeld`. `downloading`, `verifying`, `installing`, `ready`, `restarting` and `error` always show. `idle` and `up-to-date` never show.
  - `checkLocked(phase)`: true in `checking`, `downloading`, `verifying`, `installing`, `ready` and `restarting`.
  - `retryKind(view)`: a failed check retries the check. A failed install retries the install of the version on screen, or a check when no release is known. With no operation started in this session (after a reload), a known release that is not notify-only means install, and anything else means check.
  - `readyLine(version)`: "Version X is ready. Restart to finish updating." (without a version: "Update ready. Restart to finish updating.").
  - `settingsStatus(view)`: the Settings status line.
  - `downloadFraction(progress)` (`null` when the total is unknown) and `formatBytes(n)`. `formatBytes` promotes to the next unit when rounding would read 1024, so 1048524 bytes reads "1.0 MB", not "1024 KB".

### Banner (`UpdateBanner.svelte`)

Rendered by `DashboardShell` below the header and above the error banner and the search toolbar. It is the only place the dashboard shows update progress. It does not render on the setup or startup-error screens.

| Phase | Title | Detail | Buttons and link |
| --- | --- | --- | --- |
| `available` | Version X is available | "You have version Y.", plus "Download size Z." when the size is known | **Install** (not for notify-only), **Later**, and **Release notes** |
| `available`, notify-only | Version X is available | The notify reason | **Later** and **Release page** (no Install) |
| `checking` (only when `checkHeld`) | Checking for updates… | none | none |
| `downloading` | Downloading version X | "A of B (N%)" with a determinate meter; "A downloaded" when the total is unknown (indeterminate); "Preparing download…" before the first byte | **Cancel** (shows "Canceling…" until the download ends) |
| `verifying`, `installing` | Verifying download… / Installing update… | none (indeterminate meter) | none |
| `ready` | `readyLine` | Restarting closes the app and cancels a running sync. The update then applies. | **Restart now** |
| `restarting` | Restarting… | This can take up to 30 seconds. (indeterminate meter) | none |
| `error`, retry is install | Could not update to version X | The error sentence | **Try again** (install) and **Release page** |
| `error`, retry is check | Could not check for updates | The error sentence | **Try again** (check); **Release page** only when the build is notify-only |

- The release link needs a known release. It is shown in `available`, and in `error` when the retry is install or the build is notify-only. A failed check that found no release shows no link. Its label is "Release page" when the phase is `error` or the build is notify-only; otherwise "Release notes".
- The link keeps its real `href`. Clicks go to `Browser.OpenURL`, so the webview does not navigate. A failed open shows "Could not open the browser. Visit URL to read it." inline; the URL is never the last words of a sentence.
- `Install`, `Restart now` and `Try again` are disabled while `acting` is set. `Cancel` is disabled while `canceling` is set. `Later` is never disabled.
- The notice from `install()` shows as a plain line under the detail. A refusal from Go (busy, ready-first) shows its sentence in the banner and keeps the colour of an error. `ready` keeps the good-news colour.

Focus:

- A click on a button starts a change that removes or disables the button. The click marks the banner as pending focus; once the DOM has caught up, focus stays where it is if it is still on an enabled control in the banner. Otherwise it moves to the title (when the banner still shows) or to the host.
- The title has `tabindex="-1"` and is a focus target. The host `div` (`tabindex="-1"`) stays mounted while the banner is hidden. When the banner goes away with focus inside it, focus moves to the host before the DOM is removed, so focus never drops to the body.

Live region:

- The host is not a live region. One persistent visually hidden `<p role="status">` (`.sr-only`) stays mounted even while the banner is hidden. It announces the title, the notify reason (only for an `available` notify-only release), the error, the notice and the link error, joined, each ending with a full stop.
- Progress text (`aria-live="off"`) and the meter's value text are never in a live region. The title does not change during a download, so progress is not announced.

### Settings section (`UpdateSettings.svelte`)

Rendered by `SettingsView`, below the library sync section. It is hidden when the updater is unavailable in this build and before the first read succeeds.

- Current version (`unknown` when the snapshot has none).
- The switch **Check for updates on startup** (`role="switch"`). Its hint says the app contacts GitHub shortly after start and downloads nothing until Install. The box is `aria-busy` while saving. A click during a save is prevented, and after the call the box shows the stored value, so a rejected change snaps back.
- **Check now** uses `aria-disabled`, not `disabled`, so it keeps focus when clicked. It is disabled (`aria-disabled="true"`) while `checkLocked` or while `acting` is set. A click on a disabled button runs nothing. A save does not disable it.
- The status line shows `settingsStatus` as plain text, not a live region. A dismissed release reads "Press Check now to show it again."
- The live announcer is a persistent visually hidden `<p class="sr-only" role="status">` that repeats the status text only while the banner is hidden. While the banner shows, it is empty, so a phase is spoken once (by the banner), not twice. Its role is never toggled.
- Errors: a rejected toggle shows `settingsError` (`role="alert"`) always. The update error (`updateError`) shows as `role="alert"` only while the banner is hidden. While the banner shows the same error, Settings does not repeat it.
